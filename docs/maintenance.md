# 长期维护约定

更新：2026-11-10。适用于图像生成实验室后续维护；复用现有规格、BMAD 执行器和发布流程。项目约束见 [AGENTS.md](../AGENTS.md)，本页负责流程与文档导航。

## BMAD 按变更分级使用

实施者开工时根据影响范围、不确定性和恢复成本选择级别，在 PR 中简述理由；发现范围扩大时调整级别。

| 级别与适用变化 | 最小流程与产物 |
| --- | --- |
| 小改动：文档、文案、局部样式、边界清楚且不改变关键契约的 Bug 修复 | 在任务或 PR 写清问题、预期结果与验证方式，直接实施；需要工作流辅助时使用 `bmad-build`。无需补写完整 PRD、架构或故事。 |
| 独立功能：新增交互或局部能力，影响范围可界定 | 先更新相关规格；缺少规格时在 `docs/implementation/` 写简短 spec，包含范围、验收、异常与兼容边界，再用 `bmad-build` 实现、审阅和验证。 |
| 重要变化：账号权限、数据库迁移、私有存储、计费或重复调用语义、发布回退契约，或跨模块且难以恢复的调整 | 核对并更新受影响的需求与架构决定；按需使用 `bmad-prd`、`bmad-architecture` 和 `bmad-create-epics-and-stories`，拆分可验收阶段，再逐项 Build，完成相关集成与恢复验证。 |

涉及重要变化时按最高影响分级，代码行数不作为降级依据。已确认的需求直接复用；只澄清会改变目标、业务规则、权限、成本或验收的未决事项。调用 BMAD 遵循[现有执行器契约](../_bmad/README.md)，沿用 `docs/planning`、`docs/implementation` 等现有目录，不另建重复规格。审阅和测试按实际风险安排，已有有效覆盖优先。

## 文档更新责任

| 责任人 | 更新或核对时机与内容 |
| --- | --- |
| 实施者（人或 AI） | 在同一变更中更新受影响的规格和操作说明；用户可见行为或入口变化时同步 README。PR 列明所依据和修改的文档，无需更新时说明原因。 |
| 审阅者 | 合并前核对需求、代码、测试与文档的一致性，以及遗漏的异常、兼容和恢复路径；历史测试结果不能替代本次变更的验证。 |
| 项目维护者 | 确认业务范围与验收条件的实质变化、待办优先级及人工验收结果；已确认决定沿用。 |
| 发布执行者 | 发布前在相关交接或运行记录中明确回退目标及兼容证据；没有目标时写明恢复路径。获授权执行后补充版本、完整提交、时间、结果和证据链接；尚未执行的层级保持待办状态。 |

上述责任可由同一人承担，记录仍须区分实施、审阅、发布与人工验收。实施者在现有 [deferred-work.md](implementation/deferred-work.md) 汇总主动延期、需后续跟踪的功能、缺陷和技术债，记录来源、影响、优先级、责任人、验收条件及状态；详情链接原规格，正在实施的任务无需重复建条目。合并前更新相关待办，关闭时附证据。

## 有效规格与状态入口

- **需求与架构：** [PRD](product/prd-account-persistence.md)、[架构决定](architecture/account-persistence/ARCHITECTURE-SPINE.md)、[Epic 与故事](planning/epics.md)保留决定及验收依据。历史 `draft`、`backlog` 和“待实现”描述按其记录时点理解。
- **实施与后续变化：** [集成交接](implementation/spec-06-integration-handoff.md)记录阶段实现与验证；后续[默认批注策略](implementation/spec-07-default-annotations.md)和[批注完成交互](implementation/spec-08-annotation-completion-flow.md)补充相应范围。新增或替代规格时，实施者同步本入口，注明影响范围与前后关系，保留历史记录。
- **协作与运行：** [协作规范](repository-contributing.md)、[基础设施规格](implementation/spec-project-infrastructure.md)、[发布与恢复手册](operations/release-runbook.md)和[发布兼容策略](../deploy/release-policy.json)分别约束 PR、部署设计、实际操作与兼容检查。

已确认决定定义预期行为，源码与运行证据说明实际状态；冲突时查证并记录差异。状态注明日期与提交或版本，按影响范围分别记录实现、本地验证、GitHub CI、Linux 制品、服务器工具、应用发布、公网及人工验收结果。不适用项无需展开，相关项未核对就写“未核对”，不从历史记录推断当前线上状态。

## 持续维护与交付

维护者每月复核待办、依赖与安全更新、备份恢复和故障记录，将需要处理的事项排入上述流程；具体运维操作沿用发布手册与现有授权边界。本页不创建定时任务。

普通发布复用一个已验证兼容的正常稳定版本作为回退目标，不为每版制作专门回退版或维护长期分支。跨数据契约变化单独评估，必要时分阶段交付兼容能力；没有兼容目标时明确维护状态与向前修复路径。备份用于灾备，不保证无损自动回滚；现有至少五份成功制品的保留规则不变，留存不代表兼容。具体记录与边界见[发布手册的回退规则](operations/release-runbook.md#回退)。

日常交付继续使用功能分支与 PR，按改动风险执行[现有检查](repository-contributing.md)。纯文档改动检查链接、表述与差异即可；代码或工作流改动运行对应检查，不降低既有 PR CI 要求。版本 PR 合并准备 Draft Release，人工 Publish 才触发部署；合并、生产操作、收费模型验收和清理分别遵守现有授权。自动化验证与真实模型效果、人工验收分别记录。
